# Suggested-menu save repair

## Cause and follow-up

An affected installation applied migration 22 while migration 21 remained unapplied. Its PostgreSQL function definitions contain different leading indentation from the original scripts. Migration 21 compares an exact multiline SQL fragment and aborts with `remove_variety_definition_mismatch: api_apply_plans(jsonb,bigint,boolean)` even when the SQL tokens are equivalent. The first version of repair 23 only tolerated leading indentation; it still failed with the same guard on Windows CRLF line endings or trailing whitespace. The updated repair handles whitespace outside quoted SQL values, including spaces, tabs and line endings. This variant has been reproduced locally; the pasted function definitions alone cannot establish which invisible whitespace is present in the hosted database.

The old portion validator still requires each recipe ingredient's `variety_role`. The new source-backed recipes intentionally omit that removed field, so saving a suggested week containing one of those recipes fails with `invalid_recipe`.

The suggestion review was also hiding the error: the application-wide notification sits outside the native modal dialog's top layer. The confirmation icon stops spinning but the review remains open. Save failures now appear inside the review, with a translated message and a safe error identifier, while preserving the suggestions for retry.

## Existing-project repair

As the project administrator, run the entire [migration 23](../supabase/migrations/202611080023_variety_compatibility_repair.sql) in the Supabase SQL editor. This repair supports the confirmed state: successful migrations 1–20 and 22, with migration 21 failing and rolling back. It completes migration 21's changes directly; do not replay migration 21 or migration 22 afterward. Existing projects that successfully applied 21 and 22 can also run 23; it makes no changes when the required function updates are already complete.

**If the first version of migration 23 failed:** copy the entire updated file again and execute it. The failed transaction rolled back; there is no successful repair to undo. The SQL guard now includes a patch number and match count if an unexpected code difference remains.

After successful execution, refresh the app and generate and save the week again. The database repair does not require a frontend deployment; the improved in-dialog error display does require deploying this frontend change.

The repair changes function bodies only. It preserves their owners, grants, security-definer settings and search paths, household isolation, ingredient membership and quantity validation, migration 22's small-weight rounding, shopping synchronization, and all existing household content and records. All patches run in one transaction.

Each patch matches the same SQL tokens as migration 21 while allowing SQL whitespace differences outside quoted values. Quoted values and SQL operators remain exact. Exactly one match is required. Other definition changes still cause a guarded failure and transaction rollback instead of a broad or unverified rewrite. Already published migrations 21 and 22 remain unchanged.

New installations follow the normal migration order through 23, including the original household bootstrap prerequisite before migration 6. Migration 23 is repeatable. It is generated by `python tools/planning/build_variety_repair.py` from the unchanged migration 21.

## Verification

The PostgreSQL integration regression recreates varying, cumulative indentation in all eight affected functions with both Unix LF and Windows CRLF line endings, tabs and trailing whitespace, applies 22 before 21, reproduces both the original migration failure and `invalid_recipe`, applies 23, and saves a previously rejected recipe through the authenticated household RPC. It checks every new global recipe's server-generated portions against the client calculation, unchanged function permissions and household records, retained ingredient/quantity checks, and repeat execution.

The existing database suite also exercises the normal migration order and a complete generated seven-day menu. English and Spanish UI tests verify that a rejected save is visible inside the review and can be retried successfully. These are local checks; the hosted project's repair still needs to be executed by its administrator.
