# Version 6 — shared batch cooking

V6 begins after the V5 changes integrated through PR #49. It adds a shared **Kitchen / Cocina** destination in the fifth navigation position, replacing Profile. The header user emoji still opens the personal profile, settings, household administration and the hidden planning history gesture. The open V5 Purchased-list PR #46 is independent of this change.

## User flow

1. Open Kitchen while online. Expand household cooking settings, select cooking weekdays/times and the shared IANA timezone. No cooking days are assumed. Choose manual consumption (default) or automatic consumption after the meal's local day ends. Optionally prioritize complete dishes over individual bases.
2. Save the menu normally, or enable **Generate week for batch cooking** in Menu. This mode ranks diet-valid, non-vetoed choices by reuse of reviewed preparations; the ordinary generation mode remains available. Review and approve the menu before saving.
3. Select a week in Kitchen and propose sessions. The preview lists preparation instructions, raw/reference ingredient totals, quantities per person/meal/date, soaking, fridge/freezer storage and the latest time to begin refrigerator defrosting. Confirm to register planned sessions. Already reserved quantities are excluded. The first view shows concise preparation summaries; portions, instructions and storage guidance expand on request. Unavailable session times are counted once per meal and grouped in a collapsed list. Past meals appear only as an omitted-meal count, not repeated ingredient/person warnings. An empty proposal offers a shortcut to cooking times and no confirmation button.
4. Register each cooked batch with the actual reference ingredient amount prepared, optional total cooked weight, cooking-finished time and chilled/stored time. A short batch covers the earliest reservations first and leaves remaining demand uncovered. Extra portions become unassigned stock. No cooked yield is guessed. Recorded cooked grams are divided proportionally by reference amounts; calories remain those of the saved menu.
5. Confirm consumption for an individual container or all eligible containers for that meal. Manual reservations remain pending after their day ends. Automatic reservations become **assumed consumption**, distinguished from confirmed consumption, on the next server observation after midnight. This catch-up is attributed to System, never to the person opening Kitchen. “Left over” explicitly returns safe stock to availability. Changing modes affects future meals only.
6. Menu, budget, recipe veto or diet changes never rewrite an already cooked composition. Affected reservations need review. Release the reservation, propose compatible future meals and explicitly confirm a new reservation. Splitting stock preserves total reference quantity and original storage deadlines.

Kitchen does **not** deduct stock from shopping, create shopping requirements, update menu quantities, or alter V5 known-intake timing. It requires a connection and does not queue offline stock edits. The fictional preview persists its ledger in session storage; real household cooking data use scoped server RPCs only.

## Compatibility and storage policy

[Reviewed cooking rules](../../content/cooking/rules.json) register explicit recipe methods, ingredient identities and supported separate preparations. Sharing an ingredient name is insufficient. Changed methods or ingredient identities disable automatic grouping; quantities and serving-size changes remain possible. Bases include explicitly separate boiled grains/legumes, with their ingredient reference states kept distinct. Legumes cooked inside a stew are not treated as separately prepared stock. Substituted complete dishes are excluded; an unchanged compatible grain base can still qualify.

Complete dishes must be the same recipe with proportional ingredient composition and nutrition references. Optional dessert is handled separately at serving time. Fresh finishes and unregistered preparations remain ordinary cooking tasks. The rule registry is a conservative desk-reviewed compatibility list, not evidence of kitchen testing or a claim that generic nutrition data certify all product labels. New or changed catalogue methods require an explicit reviewed rule before automatic batch grouping.

Conservative app defaults, based on [FSA chilling guidance](https://www.food.gov.uk/safety-hygiene/chilling) and [UK home food guidance](https://www.gov.uk/government/publications/home-food-fact-checker/home-food-fact-checker): cool rice within one hour and refrigerate for at most 24 hours; other eligible cooked preparations cool within two hours and refrigerate for at most 48 hours. The freezer cap is a **30-day product policy**, not a claim that food universally becomes unsafe at day 31. Sessions beyond these windows are not offered. Allow 24 hours for refrigerator defrosting, use defrosted stock within 24 hours from starting defrosting (a deliberately conservative deadline), and reheat once. Actual cooling/storage times and each container’s storage are confirmed when registering a batch. Cooking earlier may require freezing portions that originally fit in the fridge window. Once defrosting begins, refreezing is disabled. Expired, discarded or consumed stock cannot be reassigned.

The ingredient reference amounts describe what went into a batch. Their sum may combine different preparation states (for example dry grain and raw vegetables); it is not a claim that the sum is the final cooked weight.

## Server contract and activation

Apply **pending migration 28** after migrations 1–27, before deploying this client. Keep `app_private` unexposed. Existing clients and menu/shopping APIs continue working. No new environment variable or dependency is required.

- `get_cooking_state(household, membership)` returns shared settings, authoritative requirements derived from saved meals, physical batches/containers, server time and the household revision. Automatic consumption is reconciled during reads and audited as System. Reservations are reviewed against current authoritative meals and dietary eligibility.
- `apply_cooking_command(household, membership, operation, revision, action, payload)` handles settings, session approval, batch registration, reservations, storage transitions, consumption, leftovers, cancellation and discards. The server reconstructs composition from saved requirements; client-supplied names/ingredient lines are not trusted.
- Private ledger/rule/receipt tables have no direct client access. Scoped executor RLS, Google membership checks, household-row locks, a shared revision and operation UUID receipts prevent cross-household access, stale updates, duplicate retries and double allocation. Receipt reuse with a different actor/request fails. Reassignments split containers without changing the immutable batch composition or increasing stock.
- The existing planning-history retention function now also removes cooking operation receipts older than 90 days. The existing daily job continues calling that function; physical stock is not purged with history. History describes the action and batch concisely rather than displaying raw ledger snapshots.

Deploying this source, executing hosted SQL and installing an updated PWA remain separate operations. This implementation does not execute hosted migrations, deploy, merge a PR or tag a release. Verify migration 28, history retention, both household members, and the installed mobile app before declaring V6 production-ready.
